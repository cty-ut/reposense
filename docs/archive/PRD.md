# RepoSense — 开源项目阅读理解 Agent

## 需求文档 v1.0

---

## 一、项目概述

### 1.1 一句话描述

给 RepoSense 一个 GitHub 仓库地址，它帮你在几分钟内搞懂这个项目的架构、核心逻辑和贡献路径——把"读源码"这件最痛苦的事变成一次对话。

### 1.2 要解决的问题

开发者想参与开源项目，但面对一个陌生的代码仓库时：

- **看不懂结构** — 几百个文件，不知道哪些是核心、哪些是辅助
- **找不到入口** — 不知道程序从哪里启动，请求从哪里进来
- **理不清关系** — 不知道模块之间怎么串联、数据怎么流动
- **无从下手贡献** — 看到 issue 不知道该改哪个文件、涉及哪些逻辑

现有的解决方式（README、文档、直接读源码）要么信息不足，要么耗时过长。一个中等规模的项目，人工从零理解通常需要 **6-20 小时**。

### 1.3 目标用户

- 想参与开源贡献但无从下手的开发者
- 加入新团队需要快速了解已有代码库的工程师
- 技术选型时需要评估开源项目质量和架构的技术负责人

## 二、核心功能定义

### 2.1 功能全景

```
                    ┌─────────────────────────────────────┐
                    │           RepoSense Agent           │
                    │                                     │
  用户输入          │  ┌───────────┐   ┌───────────────┐  │   输出
  GitHub URL ──────→│  │ 项目扫描   │──→│ 架构分析      │  │──→ 项目全景报告
  自然语言问题 ────→│  │           │   │               │  │──→ 对话式解答
                    │  └───────────┘   └───────┬───────┘  │──→ 贡献指南
                    │                          │          │
                    │  ┌───────────┐   ┌───────▼───────┐  │
                    │  │ 代码检索   │←─→│ 深度问答      │  │
                    │  │           │   │               │  │
                    │  └───────────┘   └───────────────┘  │
                    │                                     │
                    │  ┌───────────────────────────────┐  │
                    │  │ 贡献引导                       │  │
                    │  └───────────────────────────────┘  │
                    └─────────────────────────────────────┘
```

### 2.2 功能一：项目全景扫描

**触发方式：** 用户输入一个 GitHub 仓库地址

**Agent 执行步骤：**

1. 通过 GitHub API 获取仓库元信息（语言、star 数、最近活跃度、贡献者数量）
2. 获取完整目录树结构
3. 识别项目类型（Web 应用 / CLI 工具 / 库 / 框架 / etc.）
4. 分析目录结构，标注每个顶层目录的职责
5. 定位入口文件（main.py / index.ts / App.java / etc.）
6. 识别配置文件和依赖信息（requirements.txt / package.json / go.mod / etc.）

**输出——项目全景报告：**

```markdown
## 项目概览
- 名称：langchain-ai/langgraph
- 一句话总结：基于图的状态机框架，用于构建可控的多步 AI Agent 工作流
- 语言：Python (89%), TypeScript (11%)
- 规模：约 45,000 行代码，320 个文件

## 技术栈
- 核心依赖：langchain-core, pydantic, asyncio
- 测试框架：pytest
- 构建工具：pyproject.toml + hatch

## 目录结构解读
├── libs/langgraph/       → 核心库代码（重点阅读）
│   ├── graph/            → 图的定义、编译、执行引擎
│   ├── checkpoint/       → 状态持久化机制
│   ├── prebuilt/         → 预制组件（create_react_agent 等）
│   └── channels/         → 状态通道系统
├── libs/sdk/             → Python SDK
├── docs/                 → 文档源文件
└── examples/             → 示例代码

## 入口与核心流程
- 用户入口：StateGraph() 类，位于 libs/langgraph/graph/state.py
- 核心流程：定义状态 → 添加节点 → 添加边 → 编译 → 执行
- 关键文件（建议按此顺序阅读）：
  1. graph/state.py       — 状态图的定义
  2. graph/graph.py       — 图的编译逻辑
  3. pregel/__init__.py   — 执行引擎（Pregel 模型）
  4. checkpoint/base.py   — 检查点机制
```

### 2.3 功能二：深度问答

**触发方式：** 用户用自然语言提问

**能回答的问题类型：**

| 类型 | 示例问题 | Agent 怎么做 |
|------|---------|-------------|
| 架构理解 | "这个项目的状态管理是怎么做的？" | 检索相关文件 → 阅读核心代码 → 总结设计思路 |
| 流程追踪 | "一个请求从进来到返回经过了哪些步骤？" | 从入口开始 → 追踪函数调用链 → 画出流程 |
| 设计意图 | "为什么用 Pregel 模型而不是普通的 DAG？" | 检索相关代码和注释 → 结合上下文推理 → 解释取舍 |
| 定位代码 | "处理错误重试的逻辑在哪？" | 语义检索 → 精确定位文件和行号 |
| 对比分析 | "这个项目和 CrewAI 的架构区别是什么？" | 基于已有知识 + 项目分析 → 对比说明 |

**关键约束：**

- Agent 引用的每一个文件路径和代码片段，**必须在仓库中真实存在**（防幻觉的核心）
- 回答必须附带具体的文件路径和行号引用
- 不确定的内容必须明确标注"不确定"，而不是编造

### 2.4 功能三：贡献引导

**触发方式：** 用户说"我想给这个项目做贡献"

**Agent 执行步骤：**

1. 通过 GitHub API 获取 Open Issues 列表
2. 筛选带有 `good first issue`、`help wanted`、`beginner` 等标签的 issue
3. 对每个候选 issue：
   - 分析 issue 描述，理解需求
   - 定位相关的源码文件和模块
   - 评估难度（简单 / 中等 / 困难）
   - 给出修改建议：该看哪些文件、可能的实现思路
4. 按难度排序，生成贡献路线图

**输出——贡献指南：**

```markdown
## 推荐的贡献路径

### 🟢 入门级（建议先做）

**Issue #1234: 添加 retry_policy 参数的类型检查**
- 难度：简单
- 涉及文件：libs/langgraph/graph/state.py (第 45-80 行)
- 需要做什么：在 StateGraph.__init__ 中增加参数校验
- 相关测试：tests/test_graph.py
- 预计耗时：1-2 小时

### 🟡 进阶级

**Issue #1456: 支持异步 checkpoint 存储**
- 难度：中等
- 涉及文件：libs/langgraph/checkpoint/base.py, checkpoint/aio.py
- 需要理解：checkpoint 机制的读写流程
- 建议先阅读：checkpoint/base.py 的 BaseCheckpointSaver 类
- 预计耗时：4-6 小时
```

## 三、技术架构

### 3.1 系统架构图

```
┌────────────────────────────────────────────────────────────────┐
│                         用户界面（CLI）                         │
│                  输入 GitHub URL / 自然语言问题                  │
└─────────────────────────┬──────────────────────────────────────┘
                          │
                          ▼
┌────────────────────────────────────────────────────────────────┐
│                    LangGraph 编排引擎                           │
│                                                                │
│  ┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐ │
│  │ 路由节点  │───→│ 扫描节点  │───→│ 分析节点  │───→│ 输出节点  │ │
│  │          │    │          │    │          │    │          │ │
│  │ 判断用户  │    │ 拉取仓库  │    │ 理解代码  │    │ 生成报告  │ │
│  │ 意图     │    │ 信息     │    │ 回答问题  │    │ 格式化   │ │
│  └──────────┘    └────┬─────┘    └────┬─────┘    └──────────┘ │
│                       │               │                        │
└───────────────────────┼───────────────┼────────────────────────┘
                        │               │
              ┌─────────▼─────────┐  ┌──▼───────────────┐
              │    工具层（MCP）    │  │  知识层（RAG）              │
              │                   │  │                          │
              │ • GitHub API      │  │ • 向量数据库 (ChromaDB)    │
              │ • 文件读取         │  │ • BM25 关键词索引          │
              │ • 代码解析 (AST)   │  │ • 混合检索 + RRF Rerank   │
              │                   │  │ • 语义 + 精确双路召回       │
              └───────────────────┘  └──────────────────────────┘
```

### 3.2 核心数据流

```
用户输入 GitHub URL
    │
    ▼
[路由节点] 判断意图 ─── "全景扫描" / "问问题" / "想贡献"
    │
    ├── 全景扫描 ──→ [扫描节点] ──→ GitHub API 获取结构
    │                    │
    │                    ▼
    │               [分析节点] ──→ LLM 分析目录/代码 ──→ [输出节点] ──→ 全景报告
    │
    ├── 问问题 ────→ [检索节点] ──→ 混合检索（向量语义 + BM25 关键词）
    │                    │              ↓
    │                    │         RRF Rerank 融合排序
    │                    ▼
    │               [分析节点] ──→ LLM 基于检索结果回答 ──→ [输出节点] ──→ 回答
    │
    └── 想贡献 ────→ [扫描节点] ──→ GitHub API 获取 Issues
                         │
                         ▼
                    [分析节点] ──→ LLM 分析每个 Issue ──→ [输出节点] ──→ 贡献指南
```

### 3.3 状态定义

```python
class RepoSenseState(TypedDict):
    repo_url: str                      # 仓库地址
    repo_meta: dict                    # 仓库元信息（star、语言、活跃度等）
    file_tree: list[str]               # 完整文件树
    file_contents: dict[str, str]      # 已读取的文件内容缓存
    code_summaries: dict[str, str]     # 每个文件/目录的摘要
    user_query: str                    # 用户当前的问题
    intent: str                        # 路由判断结果
    retrieved_context: list[str]       # RAG 检索到的相关代码片段
    analysis_result: str               # LLM 分析结果
    conversation_history: list[dict]   # 对话历史
    current_report: str                # 当前生成的报告
```

### 3.4 技术选型及理由

| 组件 | 选型 | 为什么选它 | 对比过什么 |
|------|------|-----------|-----------|
| 编排框架 | **LangGraph** | 图状态机，流转控制最精确；支持条件分支和循环；有状态持久化 | CrewAI（太抽象，控制力不足）、AutoGen（偏对话模式，不适合工具密集场景） |
| 大模型 | **Gemini 2.5 Flash** (主) / **Claude** (备) | Gemini 2.5 Flash 性价比极高，代码理解能力强，上下文窗口大（100 万 token）；Claude 作为备选保证质量 | DeepSeek V3（API 稳定性不足）、GPT-4（贵）、通义千问（代码理解弱） |
| 向量数据库 | **ChromaDB** | 嵌入式，无需运维，pip install 即用；对个人项目规模足够 | Qdrant（需要单独部署）、Pinecone（云服务，有成本） |
| 代码获取 | **GitHub REST API** | 官方 API，稳定可靠，无需 clone 整个仓库 | git clone（太慢，占空间大）、GitHub GraphQL（复杂度过高） |
| 代码解析 | **tree-sitter** | 支持几十种语言的 AST 解析，速度极快 | Python ast 模块（只支持 Python）、正则（不可靠） |
| 用户界面 | **CLI (Rich)** | 第一版聚焦核心功能，CLI 开发最快；Rich 库提供漂亮的终端输出 | Web UI（开发成本高，非核心价值） |

## 四、实现计划

### 第一阶段：最小可用版本（MVP） — 第 1-2 周

**目标：** 输入一个 GitHub 仓库地址，输出一份项目全景报告

具体任务：

```
□ 1.1 项目初始化
  - Python 项目结构搭建（pyproject.toml / src 目录 / tests 目录）
  - 依赖安装（langgraph, langchain, chromadb, PyGithub, rich）
  - 环境变量管理（.env — API Keys）

□ 1.2 GitHub 数据获取工具
  - 实现 get_repo_meta()     — 获取仓库元信息
  - 实现 get_file_tree()     — 获取完整目录树
  - 实现 get_file_content()  — 获取指定文件内容
  - 实现 get_issues()        — 获取 issue 列表
  - 处理 API 限流（rate limiting）和错误

□ 1.3 LangGraph 基础工作流
  - 定义 RepoSenseState
  - 实现路由节点（意图判断）
  - 实现扫描节点（调用 GitHub 工具获取数据）
  - 实现分析节点（调用 LLM 分析结构）
  - 实现输出节点（格式化报告）
  - 串联为完整 Graph 并测试

□ 1.4 全景报告生成
  - Prompt 设计：让 LLM 基于文件树和关键文件内容生成结构化报告
  - 报告模板定义（Markdown 格式）
  - 分层分析策略：先目录级概览 → 再核心文件深入
```

**第一阶段完成标志：** 输入 `https://github.com/langchain-ai/langgraph`，5 分钟内输出一份准确的全景报告。

---

### 第二阶段：代码理解与问答 — 第 3-4 周

**目标：** 用户可以对已扫描的仓库提出自然语言问题，得到有代码引用的准确回答

具体任务：

```
□ 2.1 代码索引系统（RAG + BM25 混合检索）
  - 实现代码分块策略（按函数/类切分，而非固定行数）
  - 集成 Embedding 模型（ChromaDB 内置 all-MiniLM-L6-v2）
  - 将代码块向量化并存入 ChromaDB
  - 实现 BM25 关键词索引（rank_bm25），与向量索引同步构建
  - 实现混合检索：向量语义召回 + BM25 关键词召回 → RRF 融合排序
  - 语义检索擅长自然语言问题，BM25 擅长精确函数名/变量名查找

□ 2.2 问答工作流
  - 在 LangGraph 中添加问答路径
  - 实现检索节点：混合检索（向量 + BM25）+ 直接读文件（read_file）
  - 实现回答节点：基于检索结果 + 问题生成回答
  - 回答中必须包含文件路径和代码引用

□ 2.3 防幻觉机制
  - 校验层：Agent 引用的每个文件路径必须在 file_tree 中真实存在
  - 代码引用校验：引用的代码片段必须与实际文件内容匹配
  - 不确定性标注：LLM 把握度低时明确标注
```

**第二阶段完成标志：** 能准确回答"这个项目的入口在哪？""XX 功能的实现逻辑是什么？"，且所有代码引用真实有效。

---

### 第三阶段：贡献引导 — 第 5 周

**目标：** 自动分析 Open Issues，生成带有代码定位的贡献路线图

具体任务：

```
□ 3.1 Issue 分析
  - 获取并筛选 Open Issues（优先 good first issue 标签）
  - LLM 分析每个 issue 的描述，提取需求
  - 将 issue 需求与代码库关联（语义匹配相关文件）

□ 3.2 贡献路线图生成
  - 难度评估（基于涉及文件数量、修改范围、依赖复杂度）
  - 生成每个 issue 的修改建议（该看哪些文件、可能的实现思路）
  - 按难度排序输出

□ 3.3 多轮对话
  - 支持用户针对某个 issue 继续追问
  - 维护对话历史上下文
```

**第三阶段完成标志：** 输出的贡献指南中，issue 与代码定位的关联准确率 ≥ 70%。

---

### 第四阶段：生产级打磨 — 第 6-7 周

**目标：** 从"能用"变成"好用 + 简历上写得出量化数据"

具体任务：

```
□ 4.1 可观测性
  - 接入日志系统，记录每个节点的执行时间、Token 消耗
  - 统计每次分析的总成本（Token 数 × 单价）
  - 生成执行报告：耗时、成本、检索命中率

□ 4.2 错误恢复
  - GitHub API 超时/限流 → 自动重试 + 指数退避
  - LLM 返回格式错误 → 重新请求 + 格式约束
  - 单个文件分析失败 → 跳过并标注，不影响整体

□ 4.3 性能优化
  - 大型仓库（>1000 文件）的分层扫描策略
  - 文件内容缓存，避免重复 API 调用
  - Token 预算管理：设置单次分析的 Token 上限

□ 4.4 评估体系
  - 选取 10 个不同规模/语言的知名开源项目作为测试集
  - 人工标注"正确答案"（项目架构、入口文件、核心模块）
  - 自动化评估脚本：对比 Agent 输出与标注答案
  - 输出准确率、召回率、F1 指标
```

## 五、项目边界——明确不做什么

| 不做 | 原因 |
|------|------|
| Web UI | 第一版聚焦核心能力，CLI 够用；Web UI 是锦上添花，可以以后加 |
| 自动提交 PR | 超出"理解项目"的范畴，且风险高 |
| 私有仓库支持 | 需要 OAuth 认证流程，增加复杂度，MVP 阶段不必要 |
| 支持所有编程语言的深度解析 | 第一版聚焦 Python/TypeScript/Go 三种主流语言 |
| 实时代码监控 | 不是实时工具，是按需分析工具 |

## 七、风险与应对

| 风险 | 可能性 | 影响 | 应对策略 |
|------|--------|------|---------|
| GitHub API 速率限制（60 次/小时未认证） | 高 | 大型仓库扫描中断 | 使用 Personal Access Token（5000 次/小时）；实现请求缓存 |
| 大型仓库超出 LLM 上下文窗口 | 高 | 无法一次性分析所有代码 | 分层扫描：先目录摘要 → 再核心文件深入；代码分块 + RAG 检索 |
| LLM 幻觉（编造不存在的文件/函数） | 高 | 报告不可信 | 校验层强制检查每个引用；Prompt 明确要求"不确定时说不确定" |
| Gemini API 不稳定或限流 | 中 | 分析中断 | 配置备选模型（Claude）；实现自动降级切换 |
| tree-sitter 对某些语言支持不完善 | 低 | 代码解析不准确 | 降级为基于正则的简单解析；第一版聚焦 Python/TS/Go |
